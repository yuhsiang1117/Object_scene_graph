# osg 動態場景 ObjectNav：進度報告

---

## 一、目前成果

### 1.1 我們建了什麼

一個**動態場景**下的 ObjectNav 系統與評測基準。與一般 ObjectNav 的差別是：
地圖不是「不完整」，而是**主動地錯**——它自信地說物體在 A 處，而物體已經在 B 處。

評測是兩趟式的：

* **第一趟**：在靜態佈局裡自由建圖，存成一張地圖。
* **第二趟**：物體被搬走後，agent 從**那張舊圖**出發去找。

規模：**3 個場景 × 96 個 episode**，搬移分 `in_anchor`（中位移 0.72 m）
與 `cross_anchor`（中位移 6.06 m）各半。成功判準用 habitat 標準：
與最近的 authored view point 測地距離 ≤ 0.18 m。

### 1.2 成功率

| 條件 | 主要改動 | SR | SPL |
|---|---|---|---|
| A | 基線 | 0.365 | 0.201 |
| B0 | + identity channel | 0.385 | 0.208 |
| B | + VLM 當候選閘門 | 0.260 | 0.140 |
| **C0** | + 高解析度（1280） | **0.458** | 0.220 |
| E–H | 搜尋先驗、frontier 退休、逐類別門檻 | 0.427–0.448 | ~0.22 |
| **K**（目前） | + 修正兩個目標的查詢字串 | **0.448** | 0.218 |

**0.365 → 0.458**，之後在 0.43–0.46 之間持平。C0 與 K 的差距（0.458 vs 0.448）
只有一個 episode，而我們量到的 run-to-run 雜訊**正好就是一個 episode**（見 1.4）。

### 1.3 幾個機制層面的明確成果

這些比 SR 更能說明系統做對了什麼：

| 成果 | 數字 |
|---|---|
| identity channel 消除 livelock | 單一 episode 對同一錯誤 track 的重複 commit **251 → 6 次**；livelock episode 7 → 0 |
| 修正誤報氾濫（cracker box） | 一個房子裡的一個箱子，地圖裡有 15 個 track → 1 個；SR 0.143 → 0.429 |
| 修正查詢字串（湯罐頭） | in-situ recall **0.03 → 0.19**；該目標 SR **0.083 → 0.583** |
| 整體感知改善（I → K） | in-situ recall 0.357 → 0.471；只有誤報的 episode **20 → 6**；逾時 43 → 37 |
| 定位品質 | 有 track 落在物體 0.25 m 內時，SR = **0.89**；超過 2 m 時 SR = 0.03 |

### 1.4 一個意外得到的重要數字

一次操作失誤讓同一個條件被啟動了兩次，兩次都跑完 96 個 episode。
這給了我們這個基準的**第一組重複實驗**：

* SR **0.438 vs 0.427**
* in-situ recall 0.516 vs 0.550
* **七個目標裡有六個的 per-target SR 完全相同**

另一組（H 與 I，I 只加了不改變行為的儀器）給出 0.448 vs 0.438。
**兩組獨立的重複實驗都指向：run-to-run 雜訊約一個 episode。**

這件事很重要，因為它讓「兩三個 episode 的差異」變成**可以解讀的訊號**，
而不是自動被當成雜訊丟掉。

## 二、presence filter：核心機制

### 2.1 一句話

> **「沒看到」有兩種可能：東西真的不在了，或是我根本沒看清楚。
> presence filter 就是替每一次「沒看到」算出它有多少證據力的機器。**

### 2.2 為什麼需要它

你記得室友的杯子在餐桌上。今天回家你**沒看到**杯子。它被拿走了嗎？

* 從門口**匆匆瞄一眼** → 幾乎什麼都不能說明，可能被水壺擋住了。
* 站在桌前**仔細看過** → 那多半真的被拿走了。

同一句「我沒看到」，證據力天差地遠。
DualMap 的作法是把失敗的候選丟進一個查詢結束就清空的忽略清單——
等於把這個區別整個丟掉。

### 2.3 三個組成

**（a）信念，像信用分數。** 不說「在／不在」，而是給一個分數 `ℓ`，每次觀測加減分。
用分數而不用機率，是因為機率要做乘法、分數只要加減。

| 分數 `ℓ` | 機率 `p` | 白話 |
|---|---|---|
| +3 | 0.95 | 幾乎確定還在 |
| +1.5 | 0.82 | 蠻相信還在 |
| 0 | 0.50 | 完全不知道 |
| −1.5 | 0.18 | 蠻相信不在了 |

**（b）`E`：你到底有沒有真的看。** 法庭上證人說「我沒看到兇手」，
法官會先問「**當時你人在現場、看得到門口嗎？**」不在現場的證詞沒有價值。

我們用**深度相機**幾乎免費地回答它：

* 量到的深度**比預期更遠** → 物體背後的桌面露出來了 → 我確實看得到 → `E=1`
* 量到的深度**比預期更近** → 有東西擋在前面 → `E=0`
* 那個位置不在畫面裡 → `E=0`

**（c）`r`：如果它在，我這一眼看到的機率。** 由投影面積、距離、入射角算出來
（logistic regression）。這是「匆匆瞄一眼」和「仔細看過」的量化。

### 2.4 完整例子：一個碗

建圖時碗在餐桌上。第二趟開始前，碗被搬到 **1 公尺外的櫃子上**。
agent 拿到舊地圖，它**以為**碗還在餐桌上。

| 時間 | 發生什麼 | `E` | 看到? | `r` | 分數變化 | 新的 `p` |
|---|---|---|---|---|---|---|
| 起點 | 從舊地圖載入 | — | — | — | `ℓ = 1.50` | **0.82** |
| 走廊上 | 碗的位置不在畫面裡 | **0** | — | — | `+0.00` | 0.82 |
| 3 m 外瞥見餐桌 | 看得到，但沒偵測到 | 1 | 否 | 0.15 | `−0.11` | **0.80** |
| 走到 1.2 m 正對餐桌 | 看得到，還是沒偵測到 | 1 | 否 | 0.88 | `−2.07` | **0.34** |
| 同一刻 | 低於門檻 0.45 → **退出候選**，不再往餐桌走 | | | | | |
| 掃視時 | 在櫃子上偵測到碗 | 1 | **是** | 0.88 | 新 track `+2.87` | **0.95** |
| 之後 | agent 改往櫃子前進 | | | | | |

**重點在第三、四列**：同樣是「沒看到」，一次扣 0.11、一次扣 2.07，**差了近 20 倍**。

### 2.5 公式（只有兩行）

`q` = 誤報率，預設 0.05。

```
看到了         ： ℓ += log( r / q )              r=0.88 → +2.87
該看到卻沒看到 ： ℓ += log( (1−r) / (1−q) )      r=0.88 → −2.07
                                                r=0.15 → −0.11
沒機會看       ： ℓ += 0
```

直覺：**`r` 越高，「沒看到」的懲罰越重——因為你越應該看到它，沒看到就越可疑。**

因為公式只吃 `(r, q)`，**任何感測器都能接**。VLM 的 `r=0.85, q=0.02`，
一次「沒看到」是 `−1.88`，比偵測器重一倍——一次可信的查看抵兩次普通的，
不需要寫任何融合程式碼。

### 2.6 拿掉其中一塊會怎樣（三項都是我們真的踩過的坑）

| 拿掉 | 後果 |
|---|---|
| **`E`** | 走廊那一列也扣分。agent 光是在屋裡走動，信念就一路下滑——**它會「忘記」它從沒查證過的東西** |
| **`r`**（改用常數 0.6） | 3 m 外那一眼就扣 0.86，連續三次遠遠瞥過去 `p` 從 0.82 掉到 **0.25**——**還沒走到桌前就放棄了正確目標** |
| **「沒有吸收態」** | 分數掉下去就永久除名。實測：587 個 track 的地圖裡唯一正確的水壺 track 被永久排除，**下一輪所有水壺 episode 開始前就不可能贏** |

## 三、Pipeline 介紹

每一個 RGB-D frame 進來，走過以下六層。

```
RGB-D frame
    │
 ①  keyframe 判斷 ──── 不是 keyframe ──→ 只更新 costmap 與控制
    │ 是
 ②  開放詞彙偵測（YOLOE）→ mask + label + score
    │
 ③  物體層：3D 橢球擬合 → 資料關聯 → presence filter 更新
    │
 ④  場景圖重建：floor → room → container → object
    │
 ⑤  決策（FSM）：要去哪裡？
    │
 ⑥  路徑規劃與控制 → 一個動作
```

**① keyframe 判斷** — 相機位姿變化超過門檻才觸發偵測。偵測是最貴的一步
（1280 解析度下約 53 ms），不能每幀都做。

**② 開放詞彙偵測** — YOLOE，輸入是一組文字類別（詞彙表），直接輸出 mask。
取代了原本的 YOLO-World + SAM 兩段式。**這一層的品質決定了系統上限**，見第四節。

**③ 物體層** — 三件事：
* **橢球擬合**：mask + 深度 → 一個 3D 橢球（位置、大小、朝向）
* **資料關聯**：這個偵測是既有 track 還是新物體
* **presence filter 更新**：對畫面內每個既有 track，判定 `E`、`Z`，更新信念（第二節）

**④ 場景圖** — 四層階層：
* `floor`：由高度分群
* `room`：由 costmap 做 Voronoi 分割
* `container`：可承載物體的表面（桌、櫃、床…），由類別 + 幾何（頂面高度 0.2–1.4 m、
  面積 ≥ 0.06 m²）判定。**這一層是搜尋的候選集合**
* `object`：一般物體

**⑤ 決策** — 有限狀態機，六個狀態：

| 狀態 | 在做什麼 |
|---|---|
| `EXPLORE` | 決定下一個要去的地方 |
| `GOTO_FRONTIER` | 前往未知邊界或某個候選表面 |
| `APPROACH` | 已鎖定候選物體，靠近它 |
| `GOTO_VERIFY_VIEW` / `VERIFYING` | 移到可觀察位置、用 VLM 確認 |
| `DONE` | 宣告到達 |

決策的核心是**把探索與再搜尋放進同一個式子**。經典搜尋理論（Koopman；Stone 1975）
說最佳查看順序是依 `b·d/c`（信念 × 這次查看能發現的機率 ÷ 前往成本），
而 frontier 選擇**本來就在算這個索引**（score ÷ path_cost）。
所以我們沒有新增目標函數或規劃器，只是把**候選集合擴大**到「物體可能被搬去的表面」：

```
候選 = { 未探索的 frontier }  ∪  { 場景圖裡的 container 表面 }
比大小 =  b(x) · d(x) / c(x)
```

於是「去探索未知空間」和「去重看一個已知桌面」變成**同一個可以直接比較的決策**。
DualMap 的重試迴圈做不到這件事——它只能換下一個候選，無法決定「不如去探索」。

表面的先驗 `b(x)` = 可承載性（二元）× 語意親和度 × 離上次已知位置的距離。
每查看一次而沒找到，`b ← b·(1−d)`——**降低，但不歸零**。

**⑥ 規劃與控制** — Voronoi 圖（GVG）為主、A* 為備援；WaypointController 輸出離散動作。

**多次嘗試**：agent 宣告到達但沒有得分時，**地圖保留所有學到的東西**
（信念、已搜尋的表面、沿途新建的物體），只重置導航狀態，然後再試一次。
這是刻意照抄 DualMap 的 protocol——否則我們的評測會比它嚴格。

## 四、目前遇到的問題

### 4.1 感知全面改善，SR 卻不動

從 I 到 K：in-situ recall **+32%**、有正確定位的 episode 38 → 42、
只有誤報的 episode 20 → 6、沒去看的 22 → 17、逾時 43 → 37。
**SR 只動了一個 episode。**

代表瓶頸已經不在偵測。剩下 54 個沒有正確定位的 episode 裡：
**29 個是「走到 3 m 內卻沒認出」、17 個是「從來沒去看過」**。
前者要的是斜視角下的辨識，後者要的是搜尋覆蓋——都不是更好的查詢字串。

### 4.2 詞彙表處於局部最優

開放詞彙偵測頭在**自己所有類別上跑 NMS**，所以一個類別的 recall
是從鄰居身上買來的。實測：

* 把湯罐頭改名為 `cylindrical can`：它自己的 SR **0.083 → 0.500**，
  但 cracker box 的 recall 0.32 → 0.58 的同時 SR **0.667 → 0.333**。
* 三種命名方案量到的整體 SR：**0.438 / 0.438 / 0.448**。

換句話說，**改名字換來的是重新分配，不是淨增加**。
這對論文是必須揭露的問題：一個 per-class recall 對提示詞措辭如此敏感的基準
（0.03 → 0.21），不報告這個敏感度就不能宣稱「開放詞彙」。

### 4.3 基準的搬移位置不具語意 —— 最根本的問題

統計全部 114 次搬移，物體落在：**床 26 次、書桌 19 次**、桌子 6 次、櫃子 3 次……
**53 個有對應表面的搬移裡，37 個落在該類別的語意先驗表根本沒列的類別上**
（番茄湯罐頭被放到床上七次）。

用不同先驗排序真實目的地：

| 先驗 | 排第 1 的比例 | 中位排名 |
|---|---|---|
| 語意親和度 × 鄰近度 | 19/114 | 5 |
| **只用鄰近度** | **26/114** | **2** |
| 只用語意親和度 | 0/114 | 27 |
| 隨機順序 | 2/114 | 25 |

**只用語意親和度不比隨機排序好。**

這代表這個基準**無法獎勵語意搜尋先驗**——而語意搜尋後驗正是我們的主要貢獻。
這不是系統的問題，是資料的問題。

**進行中的對策**：用 HM3D 自己的標註（`.semantic.glb` 頂點顏色 + `.semantic.txt`）
當作表面類別的 ground truth，重新產生一份**語意合理**的搬移資料集
（碗放到流理台、罐頭放到櫃子，而不是床上）。
座標轉換已驗證，程式寫到一半，等 habitat collector 掛上來就能完成。

### 4.4 論文層面的缺口

| 缺口 | 說明 |
|---|---|
| **沒有跑過 DualMap baseline** | 最大的缺口。所有 SR 數字目前都沒有比較基準，而且這件事與 collector 無關——DualMap 可以在同樣三個場景上跑 |
| **static control 沒有跑** | 需要在 HM3D 原始資料集上跑靜態對照組 |
| **即時性宣稱要重講** | 高解析度之後控制迴圈約 2.4 fps（偵測 36.7 → 52.9 ms/keyframe） |
| **「四合一首創」站不住腳** | multi-floor + dynamic + open-vocab + real-time 這四項，分別已有 HOV-SG、Khronos、Hydra、Clio 覆蓋其中三項組合。真正站得住的貢獻更窄也更清楚：**把「不存在」當成一等觀測，並直接接到搜尋後驗上**，加上這個基準本身 |
