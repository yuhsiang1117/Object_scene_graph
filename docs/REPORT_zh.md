# osg 動態場景 ObjectNav：進度報告

---

## 一、目前成果

### 1.1 我們建了什麼

一個**動態場景**下的 ObjectNav 系統與評測基準。與一般 ObjectNav 的差別是：
地圖不是「不完整」，而是**主動地錯**——它自信地說物體在 A 處，而物體已經在 B 處。

評測是兩趟式的：

* **第一趟**：在靜態佈局裡自由建圖，存成一張地圖。
* **第二趟**：物體被搬走後，agent 從**那張舊圖**出發去找。

規模：**3 個場景 × 96 個 episode**，搬移分 `in_anchor`（中位移 0.72 m）
與 `cross_anchor`（中位移 6.06 m）各半。成功判準用 habitat 標準：
與最近的 authored view point 測地距離 ≤ 0.18 m。

### 1.2 成功率（in_anchor 與 cross_anchor 分開）

`in_anchor` = 物體在原地附近被移動（中位 0.72 m）；
`cross_anchor` = 被移到別的房間（中位 6.06 m）。兩者各 48 個 episode。

| 條件 | 主要改動 | **in_anchor** | **cross_anchor** | 整體 | SPL |
|---|---|---|---|---|---|
| A | 基線 | 0.438 | 0.292 | 0.365 | 0.201 |
| B0 | + identity channel | 0.458 | 0.312 | 0.385 | 0.208 |
| B | + VLM 當候選閘門 | 0.333 | 0.188 | 0.260 | 0.140 |
| **C0** | + 高解析度（1280） | 0.542 | **0.375** | **0.458** | 0.220 |
| D | + 搜尋先驗修正 | 0.479 | 0.292 | 0.385 | 0.196 |
| E | + frontier 無條件退休 | 0.500 | 0.354 | 0.427 | 0.221 |
| F | + 表面搜尋兩項 | 0.479 | **0.396** | 0.438 | 0.216 |
| G | + affinity 修正 | 0.479 | 0.375 | 0.427 | 0.211 |
| H | + 逐類別偵測門檻 | 0.521 | 0.375 | 0.448 | 0.228 |
| I | （只加儀器，不改行為） | 0.500 | 0.375 | 0.438 | 0.218 |
| J | + 換成最高分的名字 | 0.521 | 0.354 | 0.438 | 0.201 |
| **K**（目前） | + 換成具體的名字 | **0.625** | 0.271 | 0.448 | 0.218 |

**兩件被整體數字蓋掉的事：**

**（一）兩種難度差距很大，而且從頭到尾都在。** `cross_anchor` 一直比 `in_anchor`
低 0.1–0.35。這符合直覺：搬到隔壁房間時，agent 必須真的**搜尋**，
而不只是在原地附近多看幾眼。

**（二）K 的 in_anchor 是所有條件裡最高的（0.625），cross_anchor 卻掉到 0.271。**
整體 SR 0.448 把這個一升一降完全抵銷掉了。從 J 到 K（只改了兩個查詢字串）
是 in_anchor **+0.104**、cross_anchor **−0.083**——
改名字幫到了「在附近多看幾眼就找得到」的情況，卻讓需要跨房間搜尋的情況變差，
最可能的原因是新名字在整間屋子裡產生更多誤報，而長距離搜尋對誤報遠比短距離敏感。

**沒有任何一個條件同時在兩邊最好**：`in_anchor` 最高是 K（0.625），
`cross_anchor` 最高是 F（0.396），最平衡的是 C0（0.542 / 0.375）。
**這代表我們現在調的東西一直在這兩者之間做取捨，而不是把整體往上推。**

### 1.3 幾個機制層面的明確成果

這些比 SR 更能說明系統做對了什麼：

| 成果 | 數字 |
|---|---|
| identity channel 消除 livelock | 單一 episode 對同一錯誤 track 的重複 commit **251 → 6 次**；livelock episode 7 → 0 |
| 修正誤報氾濫（cracker box） | 一個房子裡的一個箱子，地圖裡有 15 個 track → 1 個；SR 0.143 → 0.429 |
| 修正查詢字串（湯罐頭） | in-situ recall **0.03 → 0.19**；該目標 SR **0.083 → 0.583** |
| 整體感知改善（I → K） | in-situ recall 0.357 → 0.471；只有誤報的 episode **20 → 6**；逾時 43 → 37 |
| 定位品質 | 有 track 落在物體 0.25 m 內時，SR = **0.89**；超過 2 m 時 SR = 0.03 |

### 1.4 一個意外得到的重要數字

一次操作失誤讓同一個條件被啟動了兩次，兩次都跑完 96 個 episode。
這給了我們這個基準的**第一組重複實驗**：

* SR **0.438 vs 0.427**
* in-situ recall 0.516 vs 0.550
* **七個目標裡有六個的 per-target SR 完全相同**

另一組（H 與 I，I 只加了不改變行為的儀器）給出 0.448 vs 0.438。
**兩組獨立的重複實驗都指向：run-to-run 雜訊約一個 episode。**

這件事很重要，因為它讓「兩三個 episode 的差異」變成**可以解讀的訊號**，
而不是自動被當成雜訊丟掉。

## 二、presence filter：核心機制

### 2.1 一句話

> **「沒看到」有兩種可能：東西真的不在了，或是我根本沒看清楚。
> presence filter 就是替每一次「沒看到」算出它有多少證據力的機器。**

### 2.2 為什麼需要它

你記得室友的杯子在餐桌上。今天回家你**沒看到**杯子。它被拿走了嗎？

* 從門口**匆匆瞄一眼** → 幾乎什麼都不能說明，可能被水壺擋住了。
* 站在桌前**仔細看過** → 那多半真的被拿走了。

同一句「我沒看到」，證據力天差地遠。
DualMap 的作法是把失敗的候選丟進一個查詢結束就清空的忽略清單——
等於把這個區別整個丟掉。

### 2.3 三個組成

**（a）信念，像信用分數。** 不說「在／不在」，而是給一個分數 `ℓ`，每次觀測加減分。
用分數而不用機率，是因為機率要做乘法、分數只要加減。

| 分數 `ℓ` | 機率 `p` | 白話 |
|---|---|---|
| +3 | 0.95 | 幾乎確定還在 |
| +1.5 | 0.82 | 蠻相信還在 |
| 0 | 0.50 | 完全不知道 |
| −1.5 | 0.18 | 蠻相信不在了 |

**（b）`E`：你到底有沒有真的看。** 法庭上證人說「我沒看到兇手」，
法官會先問「**當時你人在現場、看得到門口嗎？**」不在現場的證詞沒有價值。

我們用**深度相機**幾乎免費地回答它：

* 量到的深度**比預期更遠** → 物體背後的桌面露出來了 → 我確實看得到 → `E=1`
* 量到的深度**比預期更近** → 有東西擋在前面 → `E=0`
* 那個位置不在畫面裡 → `E=0`

**（c）`r`：如果它在，我這一眼看到的機率。** 由投影面積、距離、入射角算出來
（logistic regression）。這是「匆匆瞄一眼」和「仔細看過」的量化。

### 2.4 完整例子：一個碗

建圖時碗在餐桌上。第二趟開始前，碗被搬到 **1 公尺外的櫃子上**。
agent 拿到舊地圖，它**以為**碗還在餐桌上。

| 時間 | 發生什麼 | `E` | 看到? | `r` | 分數變化 | 新的 `p` |
|---|---|---|---|---|---|---|
| 起點 | 從舊地圖載入 | — | — | — | `ℓ = 1.50` | **0.82** |
| 走廊上 | 碗的位置不在畫面裡 | **0** | — | — | `+0.00` | 0.82 |
| 3 m 外瞥見餐桌 | 看得到，但沒偵測到 | 1 | 否 | 0.15 | `−0.11` | **0.80** |
| 走到 1.2 m 正對餐桌 | 看得到，還是沒偵測到 | 1 | 否 | 0.88 | `−2.07` | **0.34** |
| 同一刻 | 低於門檻 0.45 → **退出候選**，不再往餐桌走 | | | | | |
| 掃視時 | 在櫃子上偵測到碗 | 1 | **是** | 0.88 | 新 track `+2.87` | **0.95** |
| 之後 | agent 改往櫃子前進 | | | | | |

**重點在第三、四列**：同樣是「沒看到」，一次扣 0.11、一次扣 2.07，**差了近 20 倍**。

### 2.5 公式（只有兩行）

`q` = 誤報率，預設 0.05。

```
看到了         ： ℓ += log( r / q )              r=0.88 → +2.87
該看到卻沒看到 ： ℓ += log( (1−r) / (1−q) )      r=0.88 → −2.07
                                                r=0.15 → −0.11
沒機會看       ： ℓ += 0
```

直覺：**`r` 越高，「沒看到」的懲罰越重——因為你越應該看到它，沒看到就越可疑。**

因為公式只吃 `(r, q)`，**任何感測器都能接**。VLM 的 `r=0.85, q=0.02`，
一次「沒看到」是 `−1.88`，比偵測器重一倍——一次可信的查看抵兩次普通的，
不需要寫任何融合程式碼。

### 2.6 拿掉其中一塊會怎樣（三項都是我們真的踩過的坑）

| 拿掉 | 後果 |
|---|---|
| **`E`** | 走廊那一列也扣分。agent 光是在屋裡走動，信念就一路下滑——**它會「忘記」它從沒查證過的東西** |
| **`r`**（改用常數 0.6） | 3 m 外那一眼就扣 0.86，連續三次遠遠瞥過去 `p` 從 0.82 掉到 **0.25**——**還沒走到桌前就放棄了正確目標** |
| **「沒有吸收態」** | 分數掉下去就永久除名。實測：587 個 track 的地圖裡唯一正確的水壺 track 被永久排除，**下一輪所有水壺 episode 開始前就不可能贏** |

## 三、實驗 Pipeline：每一步用什麼工具、做什麼判斷

### 3.1 一次完整實驗（一個「條件」）的五個階段

```
① 佈局準備 ──→ ② 建圖(Pass 1) ──→ ③ 導航(Pass 2) ──→ ④ 分析 ──→ ⑤ 下一輪
   一次性          ~20 分鐘            ~4 小時          ~1 分鐘
```

| 階段 | 工具 | 做什麼判斷 | 產出 |
|---|---|---|---|
| **① 佈局準備** | `import_collector_layouts.py`<br>`author_substitute_layout.py` | 這個 YCB 資產認得出來嗎？認不出來就**換掉**（scissors 8 個名字 × 2 解析度全部 0.00 → 換成 bleach cleanser，位姿不變） | `outputs/substituted_layouts/`<br>（**原始資料完全不動**） |
| **② 建圖 Pass 1** | `campaign/rebuild_maps.sh`<br>→ `run_eval.py ycb.map_out=…` | 靜態佈局下自由探索建圖。每個目標跑一個 episode，**地圖累積**（下一個目標載入上一個的地圖再存回去） | `outputs/maps_vN/<scene>.json`<br>約 500 個 track |
| **③ 導航 Pass 2** | `campaign/run_condition.sh`<br>→ `run_eval.py ycb.map_in=…` | 物體已被搬走。agent 從**舊地圖**出發找。<br>3 場景 × 2 搬移類型 × 3 佈局 × 目標 = **96 episodes** | `outputs/<時間戳>/episodes.jsonl` |
| **④ 分析** | `analyze_campaign.py` | 三個漏斗：**感知**（有沒有在新位置建到 track）／**搜尋**（有沒有走到正確表面）／**終端**（走到了有沒有成功） | 對照表 |
| **⑤ 決定下一步** | 見 3.3 的離線工具 | 「下一個要修哪裡」——**用量測決定，不用猜** | 下一個條件 |

**關鍵設計**：第③階段只改**一件事**，其餘完全不動（同樣的地圖、同樣的 96 個 episode、
同樣的隨機種子）。這樣才能把 SR 的變化歸因到那一件事上。

### 3.2 一個 episode 內部：每一幀的判斷鏈

每個 RGB-D frame 進來，依序通過六道判斷。**任何一道沒過，後面就不會發生**。

| # | 判斷 | 工具 | 門檻／規則 | 沒過會怎樣 |
|---|---|---|---|---|
| 1 | **這幀要不要跑偵測？** | `KeyframeSelector` | 相機移動 > 0.25 m **或** 轉動 > 30° | 只更新地圖與控制，**不跑偵測**（偵測 53 ms，太貴） |
| 2 | **畫面裡有什麼？** | **YOLOE**（`yoloe-11l-seg`, imgsz 1280） | 分數 ≥ 0.30（四個弱目標降到 0.20） | 這個物體這幀不存在 |
| 3 | **這個偵測夠大嗎？** | `scene_graph.min_det_bbox_px` | 框 ≥ 1200 px | 丟掉，不建節點（碎片與雜訊） |
| 4 | **這是舊物體還是新的？** | 橢球擬合 + 資料關聯 | mask + 深度 → 3D 橢球；與既有 track 比對 | 建一個新 track |
| 5 | **既有的 track 還在嗎？** | **presence filter** | 深度比預期**遠** → `E=1`（看得到）<br>比預期**近** → `E=0`（被擋住） | `E=0` 就**不更新信念**（第二節） |
| 6 | **下一步去哪裡？** | FSM + 搜尋後驗 | 見下方 | — |

**第 6 步（決策）內部又有四個判斷**：

| 判斷 | 規則 | 為什麼 |
|---|---|---|
| **哪些 track 可以當候選？** | 標籤相符 **且** `p ≥ 0.45` **且** 被否決次數 < 2 | `p` 擋掉「走過去看過、不在」的；否決次數擋掉誤報（誤報的 `p` 壓不下去，見 2.6） |
| **候選怎麼排？** | `best_score × p` | 這是 presence filter 在查詢端的回報：看過而沒找到的會沉下去 |
| **沒有候選時，去哪？** | `b·d/c` 比大小：<br>`{未探索的 frontier}` ∪ `{場景圖裡的 container 表面}` | **探索與再搜尋是同一個決策**。DualMap 只能換下一個候選，無法決定「不如去探索」 |
| **到了之後怎麼確認？** | VLM 看一眼 → 當成 presence filter 的第二個感測器（`r=0.85, q=0.02`） | 因為公式只吃 `(r, q)`，不需要寫融合程式碼 |

**多次嘗試**：宣告到達但沒得分時，**地圖保留所有學到的東西**（信念、已搜尋的表面、
沿途新建的物體），只重置導航狀態，最多再試 2 次。
這是刻意照抄 DualMap 的 protocol——否則我們的評測會比它嚴格。

### 3.3 我們用來「決定下一步修哪裡」的工具

這些不參與導航，只用來**回答問題**。它們是這個專案最有價值的工程產出。

| 工具 | 回答什麼問題 | 成本 | 實際發現 |
|---|---|---|---|
| `probe_ycb_detection.py --mode views` | 這個物體在**最佳視角**下認得出來嗎？ | ~20 分 | scissors 全部 0.00 → 換掉 |
| `probe_ycb_detection.py --mode labels` | **換個名字**會不會比較好認？ | ~10 分 | `tomato soup can` 0.23 → `cylindrical can` 0.75 |
| `probe_ycb_detection.py --mode fp` | 這個名字會不會**誤報**？ | ~15 分 | `cracker box` 在 1280 下 300 個位姿誤報 28 次，768 下只有 2 次 |
| `rank_search_surfaces.py` | 正確的搜尋目的地**排第幾**？ | **~1 秒** | 不用模擬器，因為舊地圖已有所有候選、先驗是純函數 |
| **ground-truth 可見性儀器**<br>（在 runner 裡，agent 看不到） | agent 到底**有沒有去看**那個位置？ | 隨實驗附帶 | 把「沒去看 vs 看了沒認出」分開：**22 vs 35** |
| **in-situ recall 儀器** | 物體真的在畫面裡時，**認出來的比例**是多少？ | 隨實驗附帶 | **0.36**，而最佳視角下是 0.58——這個落差是我們原本完全看不到的 |

**工作流程**：離線工具（一秒到二十分鐘）→ **6 個 episode 的 pilot，只看機制計數器**
（巡檢次數、選擇次數、抵達次數）**不看 SR**（n=6 的 SR 沒有意義）→ 96 個 episode 完整條件。

這個流程是被教訓出來的：有一次我們用離線指標確認一個改動「全面變好」，
跑完 4 小時才發現它**把搜尋功能整個關掉了**——離線指標看的是排序，
而真正的決策看的是數值大小，兩者不是同一件事。

## 四、目前遇到的問題

### 4.1 進步在兩種難度之間互相抵銷

把成功率拆成 `in_anchor` 與 `cross_anchor` 之後（1.2 節）看得很清楚：
**沒有任何一個條件同時在兩邊最好**，而整體 SR 把一升一降抵銷掉了。
K 的 `in_anchor` 0.625 是全部條件裡最高的，`cross_anchor` 0.271 卻比 C0 的 0.375 低。

這代表最近幾輪調的東西其實是在**重新分配**，不是在提升。
往後每一次改動都應該**同時看兩個數字**，不能只看整體。

### 4.2 感知全面改善，SR 卻不動

從 I 到 K：in-situ recall **+32%**、有正確定位的 episode 38 → 42、
只有誤報的 episode 20 → 6、沒去看的 22 → 17、逾時 43 → 37。
**SR 只動了一個 episode。**

代表瓶頸已經不在偵測。剩下 54 個沒有正確定位的 episode 裡：
**29 個是「走到 3 m 內卻沒認出」、17 個是「從來沒去看過」**。
前者要的是斜視角下的辨識，後者要的是搜尋覆蓋——都不是更好的查詢字串。

### 4.3 詞彙表處於局部最優

開放詞彙偵測頭在**自己所有類別上跑 NMS**，所以一個類別的 recall
是從鄰居身上買來的。實測：

* 把湯罐頭改名為 `cylindrical can`：它自己的 SR **0.083 → 0.500**，
  但 cracker box 的 recall 0.32 → 0.58 的同時 SR **0.667 → 0.333**。
* 三種命名方案量到的整體 SR：**0.438 / 0.438 / 0.448**。

換句話說，**改名字換來的是重新分配，不是淨增加**。
這對論文是必須揭露的問題：一個 per-class recall 對提示詞措辭如此敏感的基準
（0.03 → 0.21），不報告這個敏感度就不能宣稱「開放詞彙」。

### 4.4 基準的搬移位置不具語意 —— 最根本的問題

統計全部 114 次搬移，物體落在：**床 26 次、書桌 19 次**、桌子 6 次、櫃子 3 次……
**53 個有對應表面的搬移裡，37 個落在該類別的語意先驗表根本沒列的類別上**
（番茄湯罐頭被放到床上七次）。

用不同先驗排序真實目的地：

| 先驗 | 排第 1 的比例 | 中位排名 |
|---|---|---|
| 語意親和度 × 鄰近度 | 19/114 | 5 |
| **只用鄰近度** | **26/114** | **2** |
| 只用語意親和度 | 0/114 | 27 |
| 隨機順序 | 2/114 | 25 |

**只用語意親和度不比隨機排序好。**

這代表這個基準**無法獎勵語意搜尋先驗**——而語意搜尋後驗正是我們的主要貢獻。
