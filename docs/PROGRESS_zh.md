## 零、核心機制與原理

### 0.1 問題設定

一般的 ObjectNav 假設世界是靜態的：建好圖，然後查詢。**動態場景**下這個假設會壞掉，
而且壞的方式很特別——地圖不是「不完整」，而是**主動地錯**：它自信地告訴 agent
物體在 A 處，而物體已經在 B 處。

我們的評測protocol因此是兩趟式的：

* **第一趟（mapping pass）**：在 `static` 佈局裡自由建圖，存成一張地圖。
* **第二趟（navigation pass）**：物體被搬移之後，agent 從**那張舊圖**出發去找。

搬移分兩級：`in_anchor`（中位移 0.72 m）與 `cross_anchor`（中位移 6.06 m）。
成功判準是 habitat 的標準定義：agent 與最近的 authored view point 的測地距離 ≤ 0.18 m。

### 0.2 每個方法各自來自哪裡

> **這一整節的引用來自記憶，投稿前必須逐一查證。**

| 我們用的東西 | 來自哪裡 | 我們改了什麼 |
|---|---|---|
| log-odds 二元貝氏濾波 | 教科書（Thrun/Burgard/Fox, *Probabilistic Robotics*）——和佔據柵格建圖同一套數學 | 沒改。只是把它用在「物體還在不在」而不是「這格是不是障礙」 |
| 存續性濾波（persistence filter） | Rosen, Mason & Leonard, ICRA 2016 | 他們做在**特徵**層級，我們做在**物體**層級，並且放在 abstract/concrete anchor 拆分之內 |
| 時間變化模型 | Krajník, FreMEn | 我們沒用頻域模型，只用單調衰減。列在這裡是因為它是同一個問題的另一種答案 |
| 「不在」的偵測 | Khronos (Schmid 等, 2024) 已經有 absence detection | **最接近的先前工作，必須仔細區隔**。我們的差別是用深度圖判定 `E` |
| `b·d/c` 搜尋索引與 `b ← b(1−d)` 更新 | 離散搜尋理論（Koopman 二戰反潛；Stone 1975, *Theory of Optimal Search*） | 沒改。我們做的是把 frontier 和「物體可能被搬去的表面」放進**同一個**候選集合 |
| 語意先驗引導搜尋 | Aydemir 等 T-RO 2013；Semantic Linking Maps (Zeng 等, ICRA 2020) | 我們的 `CONTAINER_AFFINITY` 是同一族的手寫表 |
| Frontier 探索 | Yamauchi 1997 | 沒改 |
| Voronoi / GVG 路徑規劃 | Choset 等的 generalized Voronoi graph | 沒改，加了 A* fallback |
| 物體以橢球表示 + 資料關聯 | QuadricSLAM (Nicholson 等)；Bowman 等 ICRA 2017 | 沒改 |
| 開放詞彙偵測 | YOLOE (ultralytics) | 取代原本的 YOLO-World + SAM，因為它直接輸出 mask |
| 抽象圖／具體圖雙層、多次導航嘗試 | **DualMap** (arXiv 2506.01950) | 我們的比較對象。protocol 刻意照抄它的多次嘗試，否則我們的評測會比它嚴格 |
| 變動的時序記錄 | TemPest (Toris & Chernova) | change log 的前身 |

**沒有已知來源、目前看起來是我們自己的三件事**：

1. **用深度圖決定 `E`**（「如果它在，這一幀會看到嗎」）——見 0.3。
2. **identity channel**——見 0.4。
3. **把崩塌的信念直接接到搜尋後驗**，而不是接到一個排序清單——見 0.5。

以及量測protocol本身（可觀測 vs 不可觀測的變動、belief latency、stale-goal rate），
但這一項還需要對照 Khronos 與 TemPest。

### 0.3 presence filter：用一個例子走完整條流程

#### 一句話版本（報告時可以直接用）

> **「沒看到」有兩種可能：東西真的不在了，或是我根本沒看清楚。
> presence filter 就是替每一次「沒看到」算出它到底有多少證據力的機器。**

#### 比喻一：為什麼「沒看到」不能直接當成「不在」

你記得室友的杯子放在餐桌上。今天回家，你**沒看到**那個杯子。它被拿走了嗎？

* 你只是**從門口匆匆瞄一眼** → 這幾乎什麼都不能說明。杯子可能被水壺擋住了。
* 你**站在桌子前面仔細看過** → 那杯子多半真的被拿走了。

同樣一句「我沒看到」，證據力天差地遠。
舊系統的作法等於**兩種都當成「不在」**（或兩種都不理會），這就是我們要修的洞。

#### 比喻二：信念像「信用分數」

我們不說「杯子在／不在」，而是給它一個**分數**，每次觀測就加減分：

* 分數高 = 很相信它還在原地
* 分數低 = 很相信它已經被搬走

這個分數就是 log-odds `ℓ`。它跟機率 `p` 是同一件事的兩種寫法：

| 分數 `ℓ` | 機率 `p` | 白話 |
|---|---|---|
| +3 | 0.95 | 幾乎確定還在 |
| +1.5 | 0.82 | 蠻相信還在 |
| 0 | 0.50 | 完全不知道 |
| −1.5 | 0.18 | 蠻相信不在了 |

**為什麼要用分數而不直接用機率？** 因為用機率要做乘法，用分數只要做加減法。
就像信用分數：遲繳一次扣 20 分，準時一年加 50 分，直接加減就好。

#### 比喻三：`E` 就是「你到底有沒有真的看」

法庭上證人說「我沒看到兇手」，法官第一件事一定是問：**「當時你人在現場、而且看得到門口嗎？」**

* 如果證人根本不在現場 → 他的證詞**沒有任何價值**，不該影響判決。
* 如果他就站在門口正對著 → 他說沒看到，那就是很強的證據。

`E` 就是這個「你當時看得到嗎」的判定。而我們**用深度相機幾乎免費地回答它**：

* 量到的深度**比預期更遠** → 碗背後的桌面露出來了 → 我確實看得到那個位置 → `E=1`
* 量到的深度**比預期更近** → 有東西擋在前面 → 我看不到 → `E=0`
* 那個位置根本不在畫面裡 → `E=0`

#### 完整例子：00829 場景的碗

**設定**：建圖時碗在餐桌上 `(−0.28, 1.01)`。第二趟開始前，碗被搬到 **1 公尺外的櫃子上**。
agent 拿到的是舊地圖，它**以為**碗還在餐桌上。

| 時間 | 發生什麼 | `E` | `Z` | `r` | 分數變化 | 新的 `p` | 為什麼 |
|---|---|---|---|---|---|---|---|
| 起點 | 從舊地圖載入碗的 track | — | — | — | `ℓ = 1.50` | **0.82** | 上一趟看過它，但過了一段時間，所以不給滿分 |
| 走廊上 | 碗的位置不在畫面裡 | **0** | — | — | `+0.00` | 0.82 | **沒機會看 ≠ 看了沒有**。證人不在現場 |
| 3 m 外瞥見餐桌 | 深度比預期遠 → 看得到；偵測器沒回報 | 1 | 0 | **0.15** | `−0.11` | **0.80** | 三公尺外本來就不太可能認出一個碗，沒看到不算證據 |
| 走到 1.2 m 正對餐桌 | 一樣看得到；偵測器還是沒回報 | 1 | 0 | **0.88** | `−2.07` | **0.34** | 這麼近、這麼大、正對著還沒看到——**碗真的不在了** |
| 同一刻 | 分數低於 `min_presence = 0.45` | | | | | | 這個 track **退出候選清單**，agent 不再往餐桌走 |
| 掃視時 | 在櫃子上偵測到一個碗 | 1 | **1** | 0.88 | 新 track `+2.87` | **0.95** | 看到是很強的證據，一次就足夠 |
| 之後 | agent 改往櫃子前進 | | | | | | |

**整條流程的重點在第三列和第四列**：同樣是「沒看到」，一次只扣 0.11，另一次扣 2.07，
差了將近 20 倍。決定這個差距的就是 `r`——「如果它真的在，我這一眼看到的機率」，
由投影面積、距離、入射角度算出來。

#### 如果拿掉其中一塊，會發生什麼

這三個對照可以直接放進報告，說明每一塊各自在擋什麼問題：

| 拿掉哪一塊 | 後果 |
|---|---|
| **拿掉 `E`** | 走廊那一列也會扣分。agent 光是在屋子裡走動、碗根本不在畫面裡，信念就一路下滑——**它會「忘記」它從沒查證過的東西** |
| **拿掉 `r`（用常數 0.6）** | 3 m 外那一眼就扣 0.86。連續三次遠遠瞥過去，`p` 從 0.82 掉到 **0.25**——**還沒走到桌子前面就已經放棄了正確的目標**。這是我們真的踩過的坑 |
| **拿掉「沒有吸收態」** | 分數掉下去就永久除名。實測過一次：一張 587 個 track 的地圖裡，唯一正確的水壺 track 被存成永久排除，**下一輪所有水壺 episode 在開始前就不可能贏** |

#### 三個數字怎麼來的

只有兩個公式，而且都只用到 `r` 和 `q`（`q` = 誤報率，預設 0.05）：

```
看到了      ： ℓ += log( r / q )           r=0.88 → log(0.88/0.05) = +2.87
該看到卻沒看到： ℓ += log( (1−r) / (1−q) )   r=0.88 → log(0.12/0.95) = −2.07
                                            r=0.15 → log(0.85/0.95) = −0.11
沒機會看    ： ℓ += 0
```

`r` 越高，「沒看到」的懲罰越重——因為你越應該看到它，沒看到就越可疑。這就是全部。

**額外好處**：因為公式只吃 `(r, q)`，任何感測器都能接。
VLM 的 `r=0.85, q=0.02`，一次「沒看到」是 `log(0.15/0.98) = −1.88`，
比偵測器重一倍——**一次可信的查看抵得過兩次普通的**，不需要寫任何融合程式碼。

### 0.4 identity channel：presence 回答不了的那個問題

presence 問「它**還在**嗎」。但**誤報是一個真的存在的物體**——你走過去看，
它確實在那裡，偵測器下一幀還會再偵測到它，信念永遠壓不下去。
實測結果是 agent 對同一個錯誤 track 在一個 episode 內 commit 了 **251 次**。

所以另開一本帳 `ObjectTrack.identity_rejections`，回答「它**是不是**我要找的那個」。
走到 track 前面、發現目標不在那裡，記在這裡而不是 presence 上。
一樣不是吸收態：門檻是 2 次，而且 episode 結束就清空——那是一次嘗試的判斷，不是永久判決。

### 0.5 搜尋後驗：我們做的事其實很小

**DualMap 的作法**：候選失敗就取下一個相似度最高的，失敗的放進一個查詢結束就丟掉的 ignore list。
等於把信念丟掉了——沒有「物體去哪了」的模型、沒有前往的成本、沒有已經找過哪裡的記憶。

**經典解**（Koopman；Stone 1975）：最佳查看順序是依 `b(x)·d(x)/c(x)`
（信念 × 這次查看能發現的機率 ÷ 前往成本），而一次失敗的查看讓信念**乘上** `(1−d)`，不是歸零。
DualMap 的 ignore list 就是這個式子的退化情形：看一次就 `b←0`，查詢結束還忘記。

**我們做的事出奇地小**：`select_frontier` 本來就在算這個索引（score ÷ path_cost）。
我們沒有新增目標函數、也沒有新增規劃器，只是把**候選集合擴大**到「物體可能被搬去的表面」。
於是「去探索未知空間」和「去重看一個已知表面」變成**同一個可以直接比大小的決策**——
DualMap 的重試迴圈做不到，因為它無法決定「不如去探索」。

表面的先驗 `b(x)` = 可承載性（二元）× 語意親和度 × 鄰近度（離上次已知位置多遠）。

### 0.6 量測儀器：這個專案最重要的工程產出

到後期我們發現每一次改進都在**猜**「agent 是沒去看，還是看了沒認出」——
這兩件事的修法完全不同，而 episode log 分不出來。於是加了兩層 ground-truth 儀器
（放在 runner 裡，**agent 完全看不到**）：

1. **可見性**：把物體真實位置投影到每一幀，剔除出畫面、在相機背後、深度圖顯示前方有遮擋者。
   沿三軸取 ±6 cm 共七點、要求至少一半可見——只測中心像素的話，
   一個九成被椅背擋住的物體也會算「看到了」。
2. **in-situ recall**：在每個「物體確實在畫面裡」的關鍵幀上，
   檢查偵測結果有沒有一個帶目標標籤、而且框住它的。
   **這才是決定勝負的 recall**，不是探測器在最佳視角量到的那個（0.36 vs 0.58）。

另外有一個**離線排序評分器**：舊地圖裡已有所有候選、`container_prior` 是純函數、
佈局檔知道正確答案，所以**不用模擬器**就能算出「真實目的地排第幾」。八小時的實驗變成一秒。

* **J 有兩次執行**（0.438 / 0.427）。那是一次意外：chain script 和手動指令相隔十秒都啟動了，

* **H → I 也是一組重複實驗**（0.448 / 0.438），因為 I 只加了不改變行為的儀器。
  兩組獨立的重複實驗都給出約**一個 episode** 的雜訊。
* **整體 SR 會蓋掉一升一降**。K 的 `in_anchor` 是所有條件裡最高的 **0.625**，

  in_anchor **+0.104**、cross_anchor **−0.083**。沒有任何一個條件同時在兩邊最好
  （`in_anchor` 最高是 K，`cross_anchor` 最高是 F 的 0.396，最平衡的是 C0）。
  **這代表我們現在調的東西一直在兩種難度之間做取捨，而不是把整體往上推。**
* **地圖重建（J、K）不是混淆因子**：逐目標比對 `maps_hires` 與 `maps_v5` 的定位誤差，
  18 項中 16 項不變、1 項變好（00880 的盤子 9.39 m → 0.07 m，這本身就是換名字的功勞）、0 項變差。

## 二、進展歷程

### 1. 早期：讓基準本身變得可信

在談任何演算法之前，我們花了很長時間確認「失敗是系統的問題，不是基準的問題」：

* **cracker box 事件**：地圖裡有 15 個 "cracker box" track，而房子裡只有一個。追下去發現四個
  互相疊加的原因——imgsz 1280 讓這個標籤變得浮濫（300 個隨機位姿有 28 個誤報，768 只有 2 個）、
  當初選 1280 的那張表是用被污染的 GT mask 量的、recall 用常數 0.6 而實測只有 0.10、
  以及一個 blacklist 穿透了 `apply_map`。修完之後 SR 0.143 → 0.429。
* **命名問題（第一次）**：`pitcher` 這個詞在這個資產上任何解析度都是 0.00 分，
  換成 `blue plastic pitcher` 就有 0.60。
* **無法挽救的資產**：scissors 在 8 個名字 × 2 種解析度下全部 0.00，中位數只有 315 px，
  偵測器叫它 "lamp"。我們用 `021_bleach_cleanser` 在**同樣的位姿**上替換掉它，
  寫進新的資料根目錄，完全不動 collector 的原始資料。
* 從 1 個場景擴到 3 個場景、96 個 episode。

### 2. 消融階梯 A → C0：0.365 → 0.458

| | A 基線 | B0 identity | B +VLM gate | C0 +hires |
|---|---|---|---|---|
| SR | 0.365 | 0.385 | 0.260 | **0.458** |

* **identity channel**（B0）：修掉 livelock。單一 episode 對同一個錯誤 track 反覆 commit
  251 次 → 最多 6 次。分數只動一點，因為那些 episode 本來就有別的問題。
* **VLM gate**（B）：**有害**。原因是它判斷的是存進地圖的縮圖，而這些目標的縮圖只有 46–101 px。
  這是「機制本身沒錯，但它看的東西不存在」。
* **高解析度**（C0）：唯一真正的贏家，而且贏在**距離**——0.8 m 時 −0.04，2.0 m 時 **+0.31**。
  它買到的是「走過去的路上瞄到」，這正是搜尋需要的。

### 3. 關鍵診斷：搜尋後驗從來沒有成功過

這是整個專案的轉折點。把 C0 的 96 個 episode 拆成漏斗：

```
物體的新位置落在某個已建圖 container 的 0.5 m 內   96/96   100%
搜尋線有被啟動                                      53/96    55%
搜尋線真的「抵達」了物體被搬去的那個表面             0/96     0%
```

**候選集合的覆蓋率是完美的，抵達率是零。** 96 個 episode 裡 agent 一共巡了 243 個表面，
沒有一個是對的。44 次成功全部來自舊地圖或 frontier 探索順路撞到。

同時排除了三件事：感知不是瓶頸（動態位姿上的 recall 0.584，與各目標 SR 的相關係數只有 +0.19）、
步數預算不是（400→500 步只多 0.02）、終端導航也不是（一旦 commit 到正確物體，77% 會成功）。

於是我們寫了 `scripts/rank_search_surfaces.py`：**不用模擬器**就能評分排序品質。
舊地圖裡已經有所有候選，`container_prior` 是純函數，佈局檔知道正確答案。
八小時的實驗變成一秒鐘。

### 4. D → K：一次改一件事

| 條件 | 改動 | SR |
|---|---|---|
| C0 | 起點 | 0.458 |
| D | 鄰近度先驗解除截斷 + frontier reach 依規劃器推導 | 0.385 |
| E | frontier 退休改為無條件 | 0.427 |
| F | surface mass 正規化 + 抵達表面後轉頭看 | 0.438 |
| G | affinity 修正 + **ground-truth 可見性儀器** | 0.427 |
| H | 逐類別 admission gate | 0.448 |
| I | in-situ recall 儀器 | 0.438 |
| J | 換成最高分的名字 | 0.438 |
| K | 換成**具體**的名字 | **0.448** |

其中幾個值得記住的：

* **D 退步了**，而且退步的原因是一個「本身正確」的修正。`_frontier_reach_m` 同時在做兩件事：
  判斷是不是無法抵達的殘樁，以及**在追蹤結束時把 frontier 擋掉**。把門檻改成規劃器真正的停止半徑
  （0.5 → 1.0 m，這在它自己的定義下是對的）之後，0.5–0.9 m 的正常抵達不再被擋，livelock 就回來了：
  每個 episode 的 frontier 選擇次數 2.15 → **20.76**。這是「修正一個門檻，順手拿掉一個沒人寫下來的互鎖」。
* **離線指標是尺度盲的**。把鄰近度先驗銳化改善了所有離線排序指標，同時**把搜尋線整個關掉**
  （六個 episode 27 次巡檢 → 1 次），因為 `_select_surface` 拿這個未正規化的數值去和 frontier 效用比大小。
  排序具有尺度不變性，那個比較沒有。

### 5. 儀器化：把猜測換成量測

到 G 為止，每一次改進都在猜「agent 是沒去看，還是看了沒認出」。這兩件事的修法完全不同，
而 episode log 分不出來。於是我們在 runner 裡加了**ground-truth 可見性儀器**
（agent 完全看不到它）：把物體真實位置投影到每一幀，剔除出畫面、在相機背後、
以及深度圖顯示前方有遮擋的情形。

第一版有個缺陷：只測**中心像素**的遮擋，所以一個九成被椅背擋住、只露出中間的物體也算「看到了」。
改成沿三軸取 ±6 cm 共七點、要求至少一半可見。這個缺陷是在條件 I 跑了四分鐘時抓到的，不是四小時後。

結果（96 episodes）：

| | 數量 | SR |
|---|---|---|
| 已定位（track 在 0.25 m 內） | 37 | **0.89** |
| **看到了（3 m 內）卻沒認出** | **35** | 0.23 |
| 只從 3 m 外看到 | 2 | 0.00 |
| **從來沒去看過** | 22 | 0.00 |

再把 59 個失敗細分（這裡我第一次分錯，必須更正）：一開始按「最近 track 的距離」分類，
看起來有 20 個是定位誤差；但其中 15 個的 track 距離**舊位置** 0.00–0.06 m——那就是原封不動的
舊 track，只是因為物體移動距離短才碰巧離新位置很近。正確的拆法是：

* **30 個是偵測問題**（走到 1.2 m 內、平均 12 幀，卻沒有任何新 track）
* **24 個是覆蓋問題**（中位搬移距離 6.84 m，17/22 是 cross_anchor）
* **5 個才是定位問題**（誤差 0.28–0.59 m）

### 6. 名字，還是名字

有了 in-situ recall（agent 真正拍到的那些幀上的 recall）之後，答案立刻浮現：

| 目標 | 有它在畫面裡的關鍵幀 | 被認出 | in-situ recall |
|---|---|---|---|
| bowl | 246 | 222 | **0.90** |
| plate | 358 | 91 | 0.25 |
| **tomato soup can** | **431** | **12** | **0.03** |

431 幀、物體中位可見度 99%、認出 12 次。11 個 episode 在 ≥3 幀可見的情況下一次都沒認出——
若每幀是獨立的 0.36 機率，這件事的機率是 0.005。**這是物體層級的辨識失敗，不是門檻或取景問題。**

重新在動態位姿上做名字探測（一次只換一個候選進詞彙表，因為「加入」量到的是 NMS 競爭而不是名字）：

| tomato soup can | | plate | |
|---|---|---|---|
| **cylindrical can** | **0.75** | **red dish** | **0.79** |
| tin can | 0.55 | red plate | 0.76 |
| *tomato soup can（原本）* | *0.23* | *plate（原本）* | *0.47* |

換名字之後（J）：罐頭的 in-situ recall 0.03 → 0.21、SR **0.083 → 0.500**；盤子 0.25 → 0.42。
但 **cracker box 的 recall 從 0.32 升到 0.58，SR 卻從 0.667 掉到 0.333**——
開放詞彙的偵測頭在自己所有類別上跑 NMS，`cylindrical can` 描述的形狀，水壺和漂白水瓶也有。
換成具體的名字（K：`tin can`、`red plate`）之後罐頭來到 **0.583**，但整體 SR 只動了一個 episode。

## 三、面對變動環境的核心策略

機制本身寫在第零節，這裡只留下**四條原則**——它們才是論文該寫、也是最貴的部分。

### 1. 沒有任何狀態是吸收態

一旦某個東西被「永久排除」，新證據就再也救不回它。這條我們違反了**四次**：
absence 直接加黑名單、黑名單穿透 `apply_map` 存進地圖檔、`_rearm_agent` 再加一次、
VLM 否決再加一次。

最貴的一次：一張 587 個 track 的地圖裡，唯一正確的水壺 track
（距真實位姿 0.00 m、分數 0.68、信念 0.82）被存成 blacklisted。
於是**下一輪所有水壺 episode 在開始之前就已經不可能贏**，而我們花了一整輪實驗才發現。

正確作法永遠是：把信念壓到 `min_presence` 以下，讓它可以被新證據救回來。

### 2. 一個問題只用一個通道回答

presence 回答「還在嗎」，identity 回答「是不是它」。把兩件事塞進同一個信念，
結果就是對同一個誤報 commit 251 次（0.4 節）。**症狀出現在導航層，病因在表示層。**

### 3. 先量測，再修

這一課我們學了三次，每次代價都是一輪完整實驗：

* VLM 候選閘門判斷的是**不存在的東西**——存進地圖的縮圖只有 46–101 px。
* 銳化搜尋先驗改善了**所有**離線排序指標，同時把搜尋線整個關掉
  （六個 episode 27 次巡檢 → 1 次）。原因是排序具尺度不變性，而
  「表面 vs frontier」的比大小沒有。
* 修正一個門檻（`_frontier_reach_m` 改成規劃器真正的停止半徑，這在它自己的定義下完全正確），
  順手拿掉了一個**沒人寫下來的互鎖**，livelock 立刻回來。

現在的流程是：**離線代理指標**（一秒）→ **6 個 episode 的 pilot，只看機制計數器
（巡檢次數、選擇次數、抵達次數），不看 SR**（n=6 的 SR 沒有意義）→ **96 個 episode 完整條件**。

### 4. 儀器優先於調參

當一個問題有兩種可能原因、而現有 log 分不出來時，
正確的下一步是**造一個能分辨它們的量測**，不是挑一個去修。
ground-truth 可見性儀器一次就終結了「沒去看 vs 看了沒認出」這個爭論——
答案是 35 比 22，和我們之前每一次的假設都相反。

## 四、我們現在遇到的問題

### 1. 感知全面改善，SR 卻不動

從 I 到 K：in-situ recall +32%、已定位 episode 38 → 42、只有誤報的 episode 20 → 6、
沒去看的 22 → 17、逾時 43 → 37。**SR 只動了一個 episode。**

這代表瓶頸已經不在偵測。K 剩下的 54 個未定位 episode 裡，29 個是看到沒認出、17 個是沒去看，
這兩者要的是**搜尋覆蓋**和**斜視角下的辨識**，不是更好的查詢字串。

### 2. 詞彙表處於局部最優

開放詞彙偵測頭在自己所有類別上跑 NMS，所以**一個類別的 recall 是從鄰居身上買來的**。
三種命名方案量到 0.438 / 0.438 / 0.448。這對論文是個必須揭露的問題：
一個 per-class recall 對提示詞措辭如此敏感（0.03 → 0.21）的基準，
不報告這個敏感度就不能宣稱「開放詞彙物體目標導航」。而且 `cylindrical can`、`red dish`
是**描述**而不是名字，這對 open-vocabulary 的宣稱本身就是扣分項。

### 3. 基準的搬移位置不具語意 —— 這是最根本的問題

統計全部 114 次搬移，物體落在：**bed 26、desk 19**、table 6、cabinet 3……
**53 個有對應表面的搬移裡，37 個落在該類別的 affinity 表根本沒列的類別上**——
番茄湯罐頭被放到床上七次。用不同先驗排序真實目的地：

| 先驗 | top-1 | 中位排名 |
|---|---|---|
| affinity × proximity | 19/114 | 5 |
| **只用 proximity** | **26/114** | **2** |
| 只用 affinity | 0/114 | 27 |
| 隨機順序 | 2/114 | 25 |

**只用 affinity 不比隨機排序好。** 這代表這個基準**無法獎勵語意搜尋先驗**——
而語意搜尋後驗正是我們的主要貢獻。這不是系統的問題，是資料的問題。

我們已經開始做語意版資料集（`scripts/author_semantic_layouts.py`，寫到一半）：
用 HM3D 自己的標註（`.semantic.glb` 頂點顏色 + `.semantic.txt`）當作表面類別的 ground truth，
而**不是**用我們自己偵測器建出來的 container 層（那會造成循環論證）。
mesh 到 habitat 的座標轉換已經驗證過是 `(x, z, −y)`——在這個轉換下 00829 的六個靜態物體
全部落在下方 0.02–0.15 m 的支撐面上。等 collector 掛上來就能完成。

### 4. 論文層面的缺口

* **沒有跑過 DualMap baseline**。所有 SR 數字目前都沒有比較基準。這是最大的缺口，
  而且跟 collector 無關——DualMap 可以在同樣三個場景、同樣的佈局上跑。
* **static control 沒有跑**（規劃是在 HM3D 原始資料集上跑）。
* **即時性宣稱要重講**：C0 之後控制迴圈約 2.4 fps（偵測 36.7 → 52.9 ms/keyframe）。
* 「首個同時具備 multi-floor + dynamic + one-shot open-vocabulary + real-time scene graph」
  這個四重宣稱是可被挑戰的（HOV-SG 有 multi-floor + open-vocab、Hydra 是 real-time multi-floor、
  Khronos 是 dynamic + real-time、Clio 是 open-vocab + real-time）。
  站得住腳的貢獻其實更窄也更清楚：**把「不存在」當成一等觀測，並把它接到一個搜尋後驗上**，加上這個基準本身。

### 5. 一個好消息：我們終於知道雜訊有多大

一次意外——chain script 和手動指令相隔十秒都啟動了條件 J——讓我們得到這個基準的**第一組重複實驗**：
SR 0.438 vs 0.427、in-situ recall 0.516 vs 0.550、**七個目標裡有六個的 per-target SR 完全相同**。

run-to-run 雜訊大約是**一個 episode**，不是二項分布界所暗示的五個。
這推翻了我們整週反覆使用的一個但書：**兩三個 episode 的差異不是自動就是雜訊**，
上面那些 cross-target 的退步是真的，而且在兩次執行裡重現到小數點後三位。
